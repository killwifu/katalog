# Katalog

Мультитенантный фотохостинг-витрина для малого бизнеса (см. `CLAUDE.md` —
контекст проекта и архитектурные инварианты).

## Требования

- Docker + Docker Compose v2
- Go 1.26+ (локальная разработка бэкенда)
- Node.js 20+ (локальная разработка фронтендов)
- [golangci-lint](https://golangci-lint.run/) v2 (`brew install golangci-lint`)
- [sqlc](https://sqlc.dev/) (`brew install sqlc`) — для `make sqlc-gen`
- libvips (`brew install vips`) — govips в воркере; нужен для сборки и тестов
- Docker должен быть запущен для `make test`: интеграционные тесты
  поднимают Postgres/Redis/MinIO через testcontainers

## Быстрый старт

```sh
make up                      # поднимает весь стек (собирает образы, применяет миграции)
curl localhost/healthz       # -> {"status":"ok"}
make down                    # останавливает стек
```

## Демо в облаке без локальной установки (GitHub Codespaces)

[![Open in GitHub Codespaces](https://github.com/codespaces/badge.svg)](https://codespaces.new/killwifu/katalog)

1. Нажмите бейдж (или Code → Codespaces → Create) — codespace сам соберёт
   и поднимет весь стек (`make up` в postCreate, первая сборка ~5–10 минут;
   прогресс — в логе создания).
2. В терминале codespace откройте порт наружу:
   ```sh
   gh codespace ports visibility 80:public -c "$CODESPACE_NAME"
   ```
   (S3-загрузки тоже идут через 80-й порт — маршрут `/katalog/orig/*` в Caddy).
3. Публичная ссылка на демо — вкладка Ports, порт 80:
   `https://<codespace>-80.app.github.dev`. Демо-данные: `make seed`.

Ссылка живёт, пока codespace запущен (останавливается после ~30 минут
простоя; перезапуск — той же кнопкой в github.com/codespaces).

После `make up` доступно:

| URL | Что |
| --- | --- |
| `localhost/` | публичные страницы: главная, `/pricing`, `/remove-bg` |
| `localhost/{slug}` | витрина магазина (Next.js SSR) |
| `localhost/app/` | обзор кабинета: сведения об альбомах, тариф, статистика, быстрый доступ |
| `localhost/app/albums` | альбомы; категории — `/app/categories`, вкладки — `/app/tabs` |
| `localhost/app/settings` | оформление и водяной знак; тарифы — `/app/billing`, статистика — `/app/stats` |
| `localhost/app/admin` | админ-зона: сводка платформы, жалобы, стоп-слова, продавцы (нужна роль `admin`) |
| `localhost/api/v1/...` | Go API |
| `localhost/abuse`, `/terms`, `/privacy`, `/content-policy` | форма жалобы и статические страницы |
| `localhost:9001` | консоль MinIO (minioadmin/minioadmin) |

Миграции применяются автоматически one-shot сервисом `migrate`,
бакет MinIO создаётся сервисом `minio-init`.

## Тарифы и биллинг

Дефолтные лимиты (меняются `PLAN_*`-переменными без пересборки):

| Тариф | Фото | Хранилище | Цена |
| --- | --- | --- | --- |
| free | 500 | 1 ГБ | 0 ₽ |
| basic | 5 000 | 10 ГБ | 490 ₽/мес |
| pro | 20 000 | 20 ГБ | 990 ₽/мес |

Квоты проверяются в presign — мягкий 403 с машинным кодом
(`photo_quota_exceeded` / `quota_exceeded` / `subscription_inactive`).
Оплата через ЮKassa: redirect на подтверждение, активация тарифа только по
вебхуку `payment.succeeded` (обработка идемпотентна — повторная доставка
события ничего не дублирует), продление — рекуррентные списания по
сохранённому способу оплаты. Просрочка оплаты: `grace` (`BILLING_GRACE_DAYS`,
загрузка заблокирована, витрина работает) → витрина скрыта; контент не
удаляется, оплата возвращает всё автоматически.

## Альбомы: пароль, корзина, категории

- **Пароль на альбом** (платные тарифы): покупатель вводит его на странице
  альбома и получает пропуск на 12 часов. Пароль закрывает страницу альбома,
  обложку в списках и поиск по подписям. Адреса файлов на CDN остаются
  публичными — кто получил прямую ссылку на картинку, откроет её и без пароля.
  На бесплатном тарифе пароль нельзя задать, сменить или снять; поставленный
  раньше продолжает действовать.
- **Корзина**: удалённые альбомы и фотографии лежат в «Удаленном»
  `TRASH_KEEP_DAYS` дней и всё это время занимают место в хранилище.
- **Категории**: альбом может лежать в нескольких категориях. Категорию можно
  скрыть с витрины или убрать с главной; главная витрины собирается из
  категорий с пометкой «На главной».
- **Файлы**: до 10 МБ на фото (jpeg/png/webp/heic).

## Интеграции (опциональные, включаются через env)

- **Платежи (ЮKassa)**: `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY`; пусто —
  оплата тарифов отключена (subscribe отвечает 503). Возврат после оплаты —
  `BILLING_RETURN_URL`.
- **Почта (SMTP)**: `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`MAIL_FROM`;
  пустой `SMTP_HOST` — письма пишутся в лог воркера (dev-режим). Письма:
  подтверждение регистрации, сброс пароля, уведомления о жалобах и блокировках,
  цепочка биллинга (оплата не прошла, витрина скрыта, оплата получена,
  автосписание не удалось, заканчивается место) — шаблоны в
  `internal/mail/templates.go`.
- **Модерация**: `ADMIN_EMAIL` — куда слать уведомления о новых жалобах;
  `STOP_WORDS` — стоп-слова подписей (через запятую), совпадение ставит фото
  флаг ручной проверки. Роль выдаётся вручную:
  `UPDATE users SET role = 'admin' WHERE email = '...'`.
- **Аналитика**: дашборд продавца в `/app/stats` (просмотры/уникальные из
  `daily_stats`, клики по каналам и топ фото из `lead_clicks` в реальном
  времени); ежемесячный email-дайджест продавцам; алерт админу на аномальный
  CDN-трафик (`TRAFFIC_ALERT_MULTIPLIER` × средненедельных просмотров,
  минимум `TRAFFIC_ALERT_MIN_VIEWS`).
- **Мониторинг**: `GET /metrics` на порту API (наружу не проксируется) —
  загрузки за сегодня, активные магазины, гистограмма латентности публичного
  API (p95 считает Prometheus); глубина очереди asynq — на `/metrics` воркера
  (порт 8081).

Полный список переменных с дефолтами — в `.env.example`.

## Деплой в прод

Один сервер с Docker, образы из GHCR, фото — в облачном S3-совместимом
хранилище. Локальный `deploy/docker-compose.yml` для прода не годится:
он держит MinIO рядом, публикует порты Postgres и Redis наружу и слушает
`:80` без TLS.

Обязательный минимум — пункты 1–2 и 5. Почта, платежи и CDN (пункты 3–4)
не нужны, чтобы поднять сервис: без них работают регистрация, кабинет,
загрузка фото и витрина. Что именно отключается — в разделе
«Что отложено» ниже.

Что нужно до первого деплоя:

1. Домен с A-записью на сервер, открытые 80 и 443 — Caddy выпускает
   сертификат Let's Encrypt сам, отдельный шаг не нужен.
2. Бакет в S3. Для Yandex Object Storage всё делает один скрипт — бакет,
   сервисный аккаунт с ключами, политика доступа, CORS и проверки:

   ```sh
   S3_BUCKET=katalog-prod-xyz APP_DOMAIN=katalog.example.ru ./deploy/s3/setup.sh
   ```

   Он печатает готовый блок `S3_*` для `.env`. Другой провайдер — те же
   политика и CORS лежат в `deploy/s3/*.json`, применить своим клиентом.
   Что в них важно:

   - анонимное чтение выдаётся **только** на `drv/*`. Ни `s3:ListBucket`,
     ни доступа к `orig/`: иначе утекают оригиналы, а листинг бакета даёт
     перечислить фото всех магазинов в обход `is_hidden` и паролей альбомов;
   - CORS обязателен. Браузер грузит оригиналы pre-signed `PUT` напрямую
     в S3, минуя API; запрос кросс-доменный и с `Content-Type` файла, то есть
     с preflight `OPTIONS`. Без правила загрузка фото не работает вообще;
   - `S3_REGION` должен совпадать с регионом провайдера (Yandex —
     `ru-central1`): он входит в scope подписи SigV4, и при несовпадении
     presigned URL отлетают с `SignatureDoesNotMatch`.

   Особенности Yandex, из-за которых порядок шагов в скрипте именно такой:

   - одной политики мало: пока у бакета не выставлен `--public-read`,
     анонимный GET отдаёт 403 при любой политике. Флаг открыл бы и `orig/`,
     поэтому доступ дальше сужает политика. **Связка обязательна: если снять
     политику, не убрав `--public-read`, публичными станут и оригиналы;**
   - появившаяся политика становится единственным источником прав для
     S3 API — сервисному аккаунту нужно явное разрешение, иначе воркер
     теряет запись и не может складывать деривативы;
   - она же блокирует остальные конфигурационные вызовы, поэтому CORS
     применяется до политики, а при повторном запуске политика сначала
     удаляется;
   - управление политикой и CORS требует роли `storage.admin`. Скрипт
     выдаёт её на время настройки и снимает на выходе — рантайму хватает
     `storage.editor`.

3. *(можно отложить)* CDN-домен на этот же бакет, **без переписывания пути**:
   адрес дериватива — `MEDIA_BASE_URL/{shop_id}/{photo_id}/{name}.webp`
   (name — small/medium/large), ключ
   в бакете — `drv/{shop_id}/...`, поэтому `MEDIA_BASE_URL` оканчивается
   на `/drv`. Origin — `<bucket>.storage.yandexcloud.net`, Host-заголовок
   оставить origin'ный. До CDN `MEDIA_BASE_URL` может смотреть прямо в бакет
   (`setup.sh` печатает готовое значение) — картинки будут отдаваться
   без кеша, но с S3-домена, а не с домена приложения.
4. *(можно отложить)* SMTP. Пустой `SMTP_HOST` — письма пишутся в лог
   воркера; регистрация и вход работают, сброс пароля практически нет.
5. Проверить, что среди существующих магазинов нет slug'ов, которые теперь
   заняты публичными страницами:
   `select slug from shops where slug in ('pricing','updates','remove-bg')`.
   Эндпоинта смены slug нет — чинить придётся в БД.

Дальше на сервере:

```sh
git clone https://github.com/killwifu/katalog.git && cd katalog
./deploy/make-env.sh           # создаст .env, сгенерирует секреты и скажет,
                               # что осталось заполнить руками
docker compose --env-file .env -f deploy/docker-compose.prod.yml up -d
```

Образы собирает CI и пушит в GHCR на каждый push в `main`: тег `latest`
и тег по sha коммита. Обновление и откат — сменой `IMAGE_TAG` в `.env`:

```sh
IMAGE_TAG=<sha> docker compose --env-file .env -f deploy/docker-compose.prod.yml up -d
```

### Что отложено

Сознательно выключено в первом деплое. Всё включается заполнением `.env`
и рестартом стека — ни пересборки образов, ни миграций не требуется.
`deploy/make-env.sh` печатает актуальный список выключенного при каждом
запуске.

| Что | Переменные | Что не работает без этого |
| --- | --- | --- |
| Почта | `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM` | письма уходят в лог воркера. Регистрация и вход работают (подтверждение почты нигде не проверяется), но сброс пароля недоступен: ссылка видна только в логе |
| Платежи | `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | `subscribe` отдаёт 503, все магазины остаются на тарифе `free` с его лимитами |
| CDN | `MEDIA_BASE_URL` | картинки отдаются напрямую из S3 без кеша. Работает, но это 95% трафика — на росте станет дорого и медленно |
| Модерация | `ADMIN_EMAIL`, `STOP_WORDS` | жалобы и алерты по трафику никуда не уходят; автофлаг подписей выключен |

Роль админа выдаётся вручную и от почты не зависит:
`UPDATE users SET role = 'admin' WHERE email = '...'`.

### Автовыкладка по SSH

Джоб `deploy` в CI после успешных тестов и сборки образов заходит на сервер,
переключает рабочую копию на задеплоенный коммит и поднимает стек с
`IMAGE_TAG` = sha этого коммита. Джоб **выключен**, пока не выставлена
переменная `DEPLOY_ENABLED=true` — иначе каждый push в `main` падал бы
на отсутствующих доступах.

На сервере нужен пользователь для деплоя, состоящий в группе `docker`,
и клон репозитория в `DEPLOY_PATH`. Ключ — отдельный, только для CI:

```sh
ssh-keygen -t ed25519 -f deploy_key -N '' -C 'github-actions'
ssh-copy-id -i deploy_key.pub deploy@<host>       # публичный — на сервер
ssh-keyscan -p 22 <host>                          # -> SSH_KNOWN_HOSTS
```

Settings → Secrets and variables → Actions:

| Secret | Что |
| --- | --- |
| `SSH_HOST` | адрес сервера |
| `SSH_USER` | пользователь деплоя |
| `SSH_KEY` | приватный ключ (содержимое `deploy_key`) |
| `SSH_KNOWN_HOSTS` | вывод `ssh-keyscan` — чтобы подмена сервера не прошла молча |

| Variable | Что |
| --- | --- |
| `DEPLOY_ENABLED` | `true` — включает джоб |
| `APP_DOMAIN` | домен, на нём же проверяется `/healthz` после выкладки |
| `DEPLOY_PATH` | путь к клону репозитория на сервере |
| `SSH_PORT` | если не 22 |

Логиниться в GHCR на сервере заранее не нужно: CI прокидывает свой
короткоживущий токен на время выкладки и разлогинивается после.
Если после `up -d` домен не отвечает на `/healthz` в течение 150 секунд,
джоб падает — молчаливой выкладки сломанного стека не будет.

Окружение джоба — `production`. В Settings → Environments на него можно
повесить ручное подтверждение, если автовыкладка на каждый коммит не нужна.

Миграции применяет one-shot сервис `migrate` при каждом старте стека,
до запуска `api` и `worker`.

### Бэкапы

Сервис `backup` (образ `deploy/backup/`) снимает `pg_dump -Fc` при старте
и дальше раз в сутки, проверяет архив `pg_restore --list` и кладёт его в
`backup/pg/<UTC-время>.dump`. Неудачный дамп повторяется через час.

Куда — два режима:

- **по умолчанию** — основной бакет, префикс закрыт политикой (аноним
  читает только `drv/*`), дампы старше `BACKUP_KEEP_DAYS` (14) удаляет
  сам сервис. Минус: тот же ключ, что у приложения, — его утечка даёт
  удалить и бэкапы;
- **отдельный бакет** (рекомендуется) — `deploy/s3/setup-backup.sh`
  создаёт бакет с версионированием и lifecycle на 14 дней и ключ, которым
  можно писать и читать, но не удалять; ключ приложения туда не ходит.
  Скрипт печатает `BACKUP_S3_*` и `BACKUP_KEEP_DAYS=0` для `.env`.

Восстановление (на сервере, из корня репозитория):

```sh
COMPOSE="docker compose --env-file .env -f deploy/docker-compose.prod.yml"
$COMPOSE exec backup sh -c 'aws --endpoint-url $S3_ENDPOINT s3 ls s3://$S3_BUCKET/backup/pg/'
$COMPOSE exec backup sh -c 'aws --endpoint-url $S3_ENDPOINT s3 cp s3://$S3_BUCKET/backup/pg/<имя>.dump /tmp/db.dump'
$COMPOSE stop api worker storefront
$COMPOSE exec backup sh -c 'pg_restore --clean --if-exists --no-owner -d $PGDATABASE /tmp/db.dump'
$COMPOSE start api worker storefront
```

Команды одинаковы для обоих режимов: в контейнере `S3_BUCKET` и ключ уже
указывают на бакет бэкапов.

Не покрыто: сами фото в S3 (оригиналы и деривативы) — бакет не копируется,
защита от удаления — версионирование бакета у провайдера. Тома `redisdata`
(кеш и очередь) и `caddydata` (сертификаты) восстанавливаются сами.

### Мониторинг доступности

Healthcheck контейнеров не заметит, что легла вся VM, — нужны внешние
проверки с алертом в Telegram. Обе бесплатные, аккаунты заводятся вручную:

- **HTTP** (UptimeRobot или аналог), раз в 5 минут:
  - `https://$APP_DOMAIN/healthz` — 200, только если API видит Postgres и
    Redis, иначе 503;
  - `https://$APP_DOMAIN/` — витрина (Next.js) отвечает.
- **Бэкап** (healthchecks.io или аналог): check с периодом 1 день и grace
  2 часа, его ping-URL — в `BACKUP_PING_URL` в `.env`. Сервис `backup`
  пингует после каждого успешного дампа; нет пинга — алерт. Так ловится и
  упавший дамп, и остановленный контейнер.

### Метрики и алерты

Prometheus собирает `/metrics` API и воркера, метрики сервера
(node-exporter) и Postgres (postgres-exporter), хранит 15 дней. Правила —
`deploy/monitoring/alerts.yml`: недоступен воркер/API/экспортёр, Postgres
лежит, очередь > 500 задач 15 минут, задачи падают окончательно, p95
публичного API > 200 мс, на диске < 20%, памяти < 10%. Мониторинг
занимает ~120 МБ, у каждого сервиса лимит памяти.

Алерты в Telegram: бот у @BotFather → `TELEGRAM_BOT_TOKEN`; написать боту
(или добавить его в группу) и взять `chat.id` из
`https://api.telegram.org/bot<токен>/getUpdates` → `TELEGRAM_CHAT_ID`.

Grafana наружу не открыта — только 127.0.0.1 сервера:

```sh
ssh -L 3001:127.0.0.1:3001 <user>@<сервер>   # и открыть http://localhost:3001
```

Логин `admin`, пароль — `GRAFANA_ADMIN_PASSWORD` (пусто — `admin`).
Дашборд «Katalog — обзор» подключается сам. Конфиги мониторинга читаются
при старте; деплой перезапускает мониторинг, если `deploy/monitoring/`
изменился.

### Ошибки (Sentry)

`SENTRY_DSN` в `.env` (бесплатный план Sentry, один проект на всё; пусто —
ошибки только в логах):

- **API и воркер** — всё, что пишется в лог уровнем Error (`internalError`
  = любые 500, `task <тип> failed` в asynq), плюс паники HTTP-хендлеров.
  Issues группируются по тексту сообщения лога;
- **кабинет и витрина** — необработанные JS-ошибки и сбои маршрутов
  кабинета. SDK и DSN (`GET /api/v1/public/config`) грузятся только при
  первой ошибке: витрина без ошибок не делает ни лишнего запроса, ни
  лишнего килобайта (+0,7 КБ на страницу, бюджет 100 КБ цел).

Что не уходит: IP, cookies, заголовки, тела запросов, query-строки адресов
(в них бывает токен сброса пароля). В настройках проекта Sentry
дополнительно включить **Security & Privacy → Prevent Storing of IP
Addresses**: IP отправителя Sentry видит на своей стороне в любом случае.

### Логи

Логи контейнеров ограничены в `docker-compose.prod.yml` (`x-logging`):
5 файлов по 20 МБ на сервис. Смотреть — `$COMPOSE logs --since 1h api`.

## Структура

```
backend/     Go: cmd/api, cmd/worker, internal/{api,worker,db,billing,mail,...}
frontend/
  cabinet/     Vite + React + TS + Tailwind + TanStack Router (раздаётся по /app/)
  storefront/  Next.js App Router: app/(marketing) — публичные страницы,
               app/[slug] — витрина магазина. Дизайн-токены в app/globals.css,
               вёрстка страниц — в CSS-модулях рядом с ними
deploy/      docker-compose.yml, Caddyfile
api/         openapi.yaml — источник правды для контрактов
migrations/  goose-миграции (schema для sqlc)
```

Фоновые задачи воркера (asynq): обработка фото, отправка писем; по крону —
агрегация статистики (00:30 UTC), биллинговый жизненный цикл (00:45),
рекуррентные списания (01:00), алерт на аномальный трафик (01:15),
ежемесячный дайджест продавцам (06:00 первого числа).

## Конвенции

- SQL только через sqlc: запросы в `backend/internal/db/queries/*.sql`,
  после изменения — `make sqlc-gen`, генерированный код коммитится.
- Каждая фича = миграция + запросы sqlc + handler + тест + обновление
  `api/openapi.yaml` (если меняется публичный контракт).
- Секреты только через env; `.env.example` поддерживать актуальным.
